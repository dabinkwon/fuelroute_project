# DEVELOPMENT — 상세 개발·검증 이력

> 실제로 무엇을 바꿨고, 왜 바꿨으며, 어떻게 검증했는지를 기록한다.
> 날짜별 F 번호·할 일·현재 완료 체크는 [TASKS.md](TASKS.md)에서만 관리한다. 이 문서는 상세 근거와 과거 개발 이력을 보존한다.

## 1. 이 문서에 기록할 내용

**개발 종료일은 2026-11-20으로 확정했다.** 사용자 지정 날짜별 F 배정과 다음 작업은 TASKS를 따른다. 여기에는 같은 할 일의 완료 체크리스트를 다시 만들지 않고, 실제 작업한 결과를 관련 F 번호에 연결한다.

| 기록 항목 | 남길 내용 |
|---|---|
| 작업일·요구사항 | 실제 작업 날짜, 관련 F 번호, 구현/문서/검증 중 작업 종류 |
| 변경 내용·이유 | 수정한 파일·함수와 달라진 동작, 그 변경이 필요한 이유 |
| 검증 방법·결과 | 사용한 Bash 명령·시나리오와 실제 결과, 모의/실호출/화면 검증 구분 |
| 문제·해결·남은 부분 | 실패 원인·수정 내용, 아직 구현하거나 검증하지 못한 범위 |
| 증거 | 테스트·실행 로그·캡처·커밋 등 확인 가능한 근거의 링크 |

작업 후 TASKS에는 짧은 결과와 이 문서의 해당 기록 링크만 남긴다. 부분 구현은 이 문서에 범위를 적고 TASKS의 전체 F 완료 체크는 미완료로 유지한다. 앞으로의 상세 기록은 위 항목을 사용하며 기존 이력은 보존한다.

TASK-010/011/012는 순서대로 완료했다. 추천·유한한 재계획 실행기와 일곱 Tool 계약을 구현했으며 아래 11장에 실제 호출·로컬 재판정·모의 검증을 구분했다. 전체 LangGraph 연결은 다음 단계다.

USER-001~USER-003의 호출 한도 확인은 완료했다. 사용자 확인값은 [2026-11-18 TASKS 완료 기록](TASKS.md#completed-2026-11-18)에 있다. 공개 이용조건·출처·현재 적용 범위는 API_USAGE에 기록해 TASK-001을 완료했다. 경로 연결 실험 TASK-005/007/008도 완료했다. 현재 위치 주유소의 0m 접근과 계산 범위 초과 입력도 별도로 검증했다.

### 계획에 담는 순서와 조건

기본 경로·안전거리 → 검색점 → 후보 → 상세 → 접근/경유 경로 → 제약 판정 → 정렬 → 추천 후보의 휴게소 보조정보 순서다. 같은 단계는 한 번만 선언하고 반복 범위는 별도 필드에 둔다. 기본 반경 5,000m·최초 검색점3개·후보3개/회·재계획2회·전체 평가9개·가격 우선은 기존 실행기의 기본 정책이며 사용자 발언으로 기록하지 않는다. 명시된 우회 상한0·정렬 선호·안전 잔량을 덮어쓰지 않는다.

상세 가격 없는 후보의 경로 조회와 추천 후보가 없는 보조 조회는 실행 조건에서 제외했다. 보조정보는 추천 후보를 정한 뒤 조회해 전체 후보의 불필요한 조회를 줄이며, 보조정보 실패로 핵심 추천을 제외하지 않는다. 후보 검색0건은 재계획 판단 대상으로, 핵심 인증/설정/한도는 중단 정책으로 구분했다. 실제 Tool 호출과 이 정책의 실행 연결은 F3007~F3009 범위다.

### 적용한 실행·실패 정책

검색점은 기본 경로와 안전 주행거리로 최대3개 생성하고 같은 주유소 ID를 합친다. 최초 조회 가격/ID 순으로 최대 `min(max_candidates,max_evaluations)`개를 한 회차 평가한다. 상세 가격이 없으면 경로를 조회하지 않고, 실제 접근이 안전거리 초과면 경유 조회를 생략한다. 요청 내 같은 경로 인자는 재사용하며 미평가 ID는 후속 재계획을 위해 남긴다.

개별 상세/경로의 NOT_FOUND/NO_ROUTE·타임아웃·파싱 오류는 후보 사유로 남겨 다른 후보를 진행한다. 기본 경로/검색 실패와 핵심 인증·설정·한도·입력 오류는 이후 호출을 중단한다. 추천이 있을 때만 휴게소를 조회하며 보조 키 누락/0건/오류는 추천을 유지하고 미확인 경고로 표시한다. 상태의 `completed`는 단계 처리가 끝났다는 뜻이며 개별 조회 성공은 공통 `ok`로 확인한다.

`execute_work_plan`은 중단 시에도 이미 얻은 부분 결과/호출을 반환한다. 공개 `execute_request`는 핵심 실패를 공통 실패(`data=null`)로 올리며 raw 그래프의 `State.execution`에는 부분 결과가 남는다. 이는 요청 내 상태이며 DB·실행 로그를 저장했다는 의미가 아니다. 정상 결과의 `replan_needed`는 후속 반복의 입력이고 이 단계에서 재계획을 실행하지 않는다.

도착 상한이 있을 때 주행 예상초+명시 정차초를 비교한다. 0분도 사용자가 명시해야 하며 미언급 정차시간은 묻는다. 날짜 없는 정상 두 시각은 같은 날의 시각차로 비교하고 날짜를 생성하지 않는다. 자정 경계는 출발/도착 날짜를 요구한다. 도착 날짜만으로23:59를 만들지 않는다. 명시 날짜 둘은KST로 계산하며 과거 도착 날짜·부족한 시각은 입력 보완이다. 미래 교통·대기시간·가격을 보장하지 않는다.

판정 결과는 `data.judgement`, 확정 후보와 갱신 비용은 `data.results`/`execution`에 반영한다. 기본 입력 준비와 최종 제약 충족은 별도 상태다. 미확인 후보는 확정 추천에서 제외하고 누락 항목/질문을 반환한다. 시간 제약으로 모든 후보가 제외되면 보조 조회를 하지 않는다. 재계획은 필요 표시만 유지하며 반복은 F3009 범위다.

## 29. F3012 실행 이벤트 발행 — 2026-11-20

**구현·검증 완료 / F3011 `802124a` 다음의 별도 기능 커밋으로 기록한다.** 실행 과정의 확인 가능한 사실을 인프로세스 이벤트로 발행하고 저장 책임은 다음 F3013으로 분리했다.

### 구현

- `schemas/events.py`에 immutable `ExecutionEvent`와 안전한 실행 ID 계약을 추가했다. 이벤트는 실행 ID, sequence, 종류, 단계, 선택 Tool/request ID/소요시간, 제한된 payload, 시간대가 있는 시각을 가진다.

- payload는 action/round index/제공사/입력 필드명/결과 크기/오류 코드/후보 수/상태만 허용한다. 좌표·가격·경로·사용자 원문·키·URL·헤더·원본 응답과 숨겨진 모델 추론은 넣지 않는다. 이벤트는 State/결과를 변경하거나 Tool을 재호출하지 않는다.
- `execute_request`의 선택 `event_bus`/`execution_id`를 연결했다. 지정 시 `data.event_stream`에 실행 ID·발행 건수·전달 실패 수를 반환한다. 기본 호출은 기존 출력과 실행을 유지하며 저장·큐는 만들지 않는다.

### 검증

## 30. F3013 실행 로그 저장 — 2026-11-20

**구현·검증 완료 / F3012 `1d662c6` 다음의 별도 기능 커밋으로 기록한다.** 이벤트 발행과 SQLite I/O를 구독 경계로 분리하고 저장 장애가 메인 실행에 전파되지 않게 했다.

### 구현

- `schemas/events.py`에 실행 세션 상태/시작·종료 시각/event count 조회 계약을 추가했다. 실행 중에는 종료 시각이 없고 completed/failed에는 시간대 있는 종료 시각이 필요하다.

- `api/chat.py`의 `POST /api/chat`은 session ID가 없으면 새 대화 ID를 만들고, 요청마다 별도
  execution ID를 만든다. 전체 `execute_request`에 SQLite Memory와 요청별 EventBus를 넘기고
  Logging Agent를 먼저 구독시켜 같은 실행을 `/api/logs/{execution_id}`에서 조회할 수 있다.
- Chat 응답은 분석·판정·재계획·F3011 최종 응답, 이벤트 건수와 로그 전달 실패 수만 typed
  모델로 노출한다. 내부 작업 계획·Tool 원문·캐시·모델 추론은 HTTP 응답에 넣지 않는다.
  로깅 장애는 EventBus 정책대로 정상 응답을 막지 않고 실패 수로 구분한다.
- `api/plans.py`는 POST/GET 목록/GET 상세/PATCH/DELETE를 F3015~F3016 Repository에 연결했다.
  저장 충돌은 201 성공 안에 알리고, revision 충돌409·없는 ID404·입력422·저장 장애503을
  기존 `{error:{code,message,request_id}}` 형식으로 정제한다.
- `api/app.py`에 Chat·Plans router를 Logs와 별도 등록했다. `/health`는 계속 DB/키와 독립적이며
  로그에는 PATCH/PUT을 추가하지 않았다. 함수/필드 설명은 OpenAPI에 전달된다.

### 검증

신규 HTTP 테스트 **5개**, 전체 **429개**와 Ruff/포맷 검사를 통과했다. 실제 Agent의 인사
분기를 오프라인 분석기로 실행해 Chat 응답의 새 IDs와 이벤트 저장, 이어지는 Logs 상세의
동일 event_count를 확인했다. 계획 HTTP 전체 CRUD, 프로세스 재연결에 해당하는 새 Repository
객체 조회, 재검증 상태, 시간 겹침 201, 오래된 revision 409, 잘못된 요청422, 없는 ID404,
Agent 설정 실패503의 공통 오류와 원문 비노출을 확인했다. 기존 F3014 테스트로 로그 삭제 후
계획 본문 보존도 유지했다. 생성 OpenAPI의 메서드 집합과 ASGI `GET /docs` 200/Swagger HTML을
확인했다.

이번 검증은 임시 SQLite·ASGI와 오프라인 인사 분기다. 실제 GMS/데이터 API 추천 HTTP 호출,
실제 uvicorn 브라우저 화면과 Netlify 연결은 수행하지 않았다. 다음은 **F3018 UI**이며 사용자
레퍼런스를 받은 뒤 화면 구조·스타일을 먼저 맞추고 실제 Backend API를 연결한다.
